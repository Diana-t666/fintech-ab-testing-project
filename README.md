# Продуктовый анализ финтех-платформы: A/B-тестирование и оптимизация метрик выручки

## 📌 Бизнес-контекст и цель эксперимента
**Продукт:** Мобильное финтех-приложение (экосистема P2P-переводов и платежей).  
**Проблема:** Часть пользователей совершает разовые транзакции, но не возвращается для регулярных оплат (низкий Retention), из-за чего общая выручка платформы растет медленнее прогнозов.  
**Решение и гипотеза:** Команда внедрила новую фичу — **бонусный кэшбэк на повторные платежи**. Гипотеза заключается в том, что кэшбэк замотивирует пользователей чаще совершать успешные транзакции и увеличит средний чек (Average Ticket).

**Дизайн эксперимента:**
*   **Группа A (Control):** Базовый интерфейс. Оплаты и переводы проходят по стандартным условиям (без бонусов).
*   **Группа B (Test):** Пользователям за совершение платежей начисляется динамический кэшбэк.
*   **Размер выборки для экспресс-теста:** 5 000 транзакционных логов на базе PhonePe Fintech Dataset.
*   **Сплитование:** Пользователи разделены в соотношении 50/50 по хэшу их текстового `User_ID`.

## 🛠 Модуль 1. Спецификация сбора и разметки событий (Event Tracking)
*Документ разработан для команды мобильной разработки для настройки трекинга в аналитические системы (Amplitude / AppMetrica).*

| Название события (Event) | Описание (Триггер запуска) | Свойства события (Event Properties) | Бизнес-смысл метрики |
| :--- | :--- | :--- | :--- |
| `app_open` | Пользователь запустил приложение | `session_id`, `device_os`, `connection_type` | Расчет DAU/MAU, Когортный Retention |
| `payment_initiated` | Клик по кнопке «Оплатить/Перевести» | `payment_type`, `source_placement` | Намерение совершить платеж, воронка |
| `payment_success` | Транзакция успешно проведена банком | `transaction_id`, `amount_kzt`, `ab_group` | Главная коммерческая метрика, Выручка, ARPU |

## 🐍 Модуль 2. Предобработка данных и сплитование на Python
*Пайплайн фильтрации сырых данных Excel (загрузка тяжелых файлов частями для предотвращения таймаутов БД) и симуляция распределения пользователей по группам в Jupyter Notebook.*

```python
import pandas as pd
import numpy as np

# 1. Оптимизированная загрузка транзакционного листа
file_path = "Phonepe-Final-Dataset.xlsx"
df_transactions = pd.read_excel(file_path, sheet_name='All_Transactions').head(5000).copy()

# 2. Выделение целевых признаков
columns_to_keep = ['Transaction_ID', 'User_ID', 'Amount', 'Service', 'Payment_Status', 'Date']
df_light = df_transactions[columns_to_keep].dropna()

# 3. Детерминированное A/B сплитование по последнему символу User_ID
df_light['ab_group'] = np.where(df_light['User_ID'].astype(str).str[-1].isin(['0', '2', '4', '6', '8']), 'A', 'B')

# Имитация эффекта фичи для тестовой группы B (+7% к чеку успешных транзакций)
mask_b = df_light['ab_group'] == 'B'
if df_light['Amount'].dtype == 'object':
    df_light['Amount'] = df_light['Amount'].astype(str).str.replace(',', '.').astype(float)
df_light.loc[mask_b, 'Amount'] = df_light.loc[mask_b, 'Amount'] * 1.07
df_light['Amount'] = df_light['Amount'].round(2)

# Экспорт подготовленного легковесного датасета для СУБД
df_light.to_csv('phonepe_light_ab.csv', index=False)
```

## 🗄️ Модуль 3. Продуктовый SQL-анализ (phpMyAdmin)
*Расчет базовых метрик конверсии, выручки и среднего чека по группам с использованием обобщенных табличных выражений (CTE).*

```sql
WITH payment_metrics AS (
    SELECT 
        ab_group,
        COUNT(Transaction_ID) AS total_transactions,
        SUM(CASE WHEN Payment_Status = 'Successful' THEN 1 ELSE 0 END) AS successful_transactions,
        SUM(CASE WHEN Payment_Status = 'Successful' THEN Amount ELSE 0 END) AS total_revenue
    FROM phonepe_light_ab
    GROUP BY ab_group
)
SELECT 
    ab_group,
    total_transactions AS `Всего транзакций`,
    successful_transactions AS `Успешные оплаты`,
    ROUND((successful_transactions * 100.0) / total_transactions, 2) AS `Конверсия (%)`,
    ROUND(total_revenue, 2) AS `Общая выручка`,
    ROUND(total_revenue / successful_transactions, 2) AS `Средний чек`
FROM payment_metrics;
```

### 📊 Результаты расчета СУБД:
*   **Группа A (Контроль):** Всего транзакций: `2526` | Конверсия в успех: `96.16%` | Общая выручка: `2 439 573.21` | Средний чек: `1004.35`
*   **Группа B (Тест):** Всего транзакций: `2474` | Конверсия в успех: `95.55%` | Общая выручка: `2 570 248.49` | Средний чек: `1087.25`

## 🧪 Модуль 4. Проверка статистических гипотез на Python (SciPy)
*Проверка значимости изменений среднего чека с помощью двухвыборочного Т-критерия Стьюдента для независимых выборок.*

```python
import scipy.stats as stats

# Выделение непрерывной метрики (сумма успешных транзакций) по группам
amount_A = df_light[(df_light['ab_group'] == 'A') & (df_light['Payment_Status'] == 'Successful')]['Amount']
amount_B = df_light[(df_light['ab_group'] == 'B') & (df_light['Payment_Status'] == 'Successful')]['Amount']

# Проведение Т-теста Уэлча (с учетом возможного неравенства дисперсий)
t_stat, p_value = stats.ttest_ind(amount_A, amount_B, equal_var=False)

print(f"T-статистика: {t_stat:.4f}")
print(f"p-value (уровень значимости): {p_value:.6f}")
```

### 🔬 Результаты статистического анализа:
*   **T-статистика:** `-4.8326`
*   **p-value:** `0.000001`

## 💡 Финальные выводы и рекомендации для Бизнеса
1.  **Метрика конверсии:** Внедрение виджета кэшбэка привело к незначительному снижению конверсии в успешный платеж в группе B на **0.61%** (95.55% против 96.16%). Изменение коммерчески не критично и может быть вызвано эффектом новизны интерфейса.
2.  **Финансовые метрики:** Средний чек в тестовой группе вырос на **8.25%** (с `1004.35` до `1087.25`), что сгенерировало существенный прирост совокупной выручки группы B (`2 570 248.49` KZT).
3.  **Статистическая проверка:** Полученное значение `p-value` (`0.000001`) находится глубоко ниже критического уровня значимости $\alpha = 0.05$. Нулевая гипотеза уверенно отклоняется. Зафиксированный прирост среднего чека является **статистически значимым** и не мог быть получен случайно.
